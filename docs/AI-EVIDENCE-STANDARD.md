# AI 证据驱动执行规范（AI-EVIDENCE-STANDARD）

> **性质**：规范性文件 —— 严格约束「AI 助手与协作 Agent 怎么表述结论、怎么获取有效证据、怎么裁决技术冲突、什么时候必须停止循环」。
> **与其它文档的分工**：
> - `AGENTS.md` §1.1 管「去哪找权威定义」（Docs-First）；
> - `docs/WORKFLOW.md` 管「按什么步骤研发与验证」（8步链路）；
> - 本规范管「**找到并执行后，结论与交付成果怎么写才经得起第三方独立复核**」。
>
> 门禁：由 `tests/unit/workflow-governance.test.ts` 锁定核心原则与要素。

## 0. 核心定位与使用准则

### 0.1 三档主张：已验证 / 推断 / 未知

对于会**直接影响系统架构、执行流程、安全性、代码正确性或最终验收**的重要结论，必须显式标明其证据档次：

| 证据标签 | 准确含义 | 达标判据（必须满足方可标此档） |
|---|---|---|
| **`[已验证]`** | 本轮已用直接证据确认无误 | 证据**可独立复现**：第三方依照你给出的命令/路径/输出片段，能获得完全相同的结论 |
| **`[推断]`** | 由已知已验证事实逻辑推演得出，尚未直接执行 | 必须明确阐明**推断链的每一步逻辑依据**，并清晰指出哪一环尚未经过直接测试验证 |
| **`[未知]`** | 当前掌握的信息不足以支持下结论 | 必须明确写出**缺少什么关键信息、谁掌握该信息、如何补充获取** |

**核心硬规则**：
1. **严禁推断当事实**：任何未经验证的推断严禁包装成「事实」汇报；
2. **严禁未知当答案**：遇到未知信息严禁由 AI 模型自发脑补「看似合理」的答案；
3. **未知是合规结论**：如实承认并标注 `[未知]` 是完全合格且受鼓励的行为，远胜于编造虚假结论；
4. **P-SRC-3 人数不是证据**：想得更久、多个 AI 意见一致、论证听起来顺畅，**均不构成证据等级的提升**。唯有真实运行输出、官方源码和权威断言才是证据。

### 0.2 避免形式主义（规范不要求什么）

为防范文档与沟通形式主义，本规范明确**不要求**以下行为：
- ❌ 不要求每句话都贴标签（普通描述、背景叙述不贴标签，仅关键技术裁决与验收结论贴标签）；
- ❌ 不要求记录每一次简单的文件阅读或琐碎终端交互；
- ❌ 不要求冗长繁复的过程流水账报告；
- ❌ 不要求无意义的重复扫描，一次定向精确定位加一次针对性验证即可。

## 1. 测试结果五态表达标准

在汇报模块测试或验证情况时，严禁使用含糊的「测试好像通过了」或「基本没问题」，必须使用精确的**五态标准**：

1. **已执行通过**：测试命令实际运行完毕，返回码为 0，且包含明确的断言通过指纹（如 `pass N, fail 0` 或 `Ran N tests`）；
2. **已执行失败**：测试命令实际运行完毕，抛出 AssertionError 或异常退出码，附带错误堆栈与失败用例名；
3. **尚未执行**：测试用例已编写或发现，但本轮尚未触发运行；
4. **无法执行**：因环境缺失（如缺少 node_modules、缺少特定操作系统能力或依赖未就绪）导致测试进程无法启动；
5. **通过但覆盖不足**：测试虽返回成功，但缺乏对边界值、异常分支或特定不变式的断言覆盖。

## 2. 交付成果 A/B/C/D/E 五类分档

任何阶段性交付或任务终结报告，交付内容必须分级清晰，严禁把「建议」冒充「已修」，严禁把「未充分验证」冒充「完全安全」：

- **A 类（已完成且通过验证）**：代码已修改，经过完整的本地静态检查与动态测试验证，有明确的运行证据与指纹；
- **B 类（已实施未充分验证）**：代码已编写落地，但受限于环境或测试集，尚未完成充分的端到端或压力验证；
- **C 类（未完成或被阻塞）**：任务尚未达成目标，当前被上游依赖、未解决的技术缺陷或外部接口阻塞；
- **D 类（仅建议未实施）**：提出了后续改进方案或架构优化建议，但当前分支未做任何代码变动；
- **E 类（剩余风险与盲区）**：本次交付后已知存在的边界风险、待观察项或测试盲区。

## 3. 评审收敛与 3 次失败停机升级机制

在多轮自我纠错或多 Agent 协作评审时，必须保证问题解决的收敛性：

- **3 次失败停机升级**：
  若在同一个技术问题或同一个测试失败上，连续尝试方案修改 3 次仍未解决，**必须立即终止自动重试循环**。
  - 整理输出三项内容：
    1. 已尝试的 3 种方案与具体改动；
    2. 每次失败的具体报错证据与定位；
    3. 核心阻塞原因与潜在技术分歧。
  - 向上级总代理或人类架构师发起技术裁决申请，严禁无限制循环试错耗尽上下文或算力。
- **已验收项重开触发条件**：
  已经通过 A 类验收的模块，只有在出现以下 4 类硬证据时方允许重新打开：
  1. 新的客观事实或官方规范更新；
  2. 发现了可稳定复现的新缺陷；
  3. 发现了明确遗漏的原始需求；
  4. 新需求与既有核心约束产生不可调和的冲突。
